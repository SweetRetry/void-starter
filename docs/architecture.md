# Architecture

Void Starter is a Turborepo + pnpm workspace with one app and two shared packages. The app deploys as a single Cloudflare Worker.

## Workspace

| Path                         | Owns                                                                                     |
| :--------------------------- | :--------------------------------------------------------------------------------------- |
| `apps/web`                   | The TanStack Start app: routes, server functions, `/api/*` routes, schema and migrations |
| `packages/ui`                | shadcn/ui components on Base UI, Retry tokens (`globals.css`), shared hooks and `cn`     |
| `packages/typescript-config` | Shared tsconfig presets                                                                  |

`apps/*` own entry points and app-specific business code. `packages/*` hold only what several apps already share, never what might be reused someday. Packages are consumed through their public `exports`.

## Inside `apps/web`

```text
apps/web/
  src/routes/             file routes: pages, layouts and /api/* server routes
  src/server/             server-only modules (*.server.ts) and server functions (*.functions.ts)
  src/components/         app components; chat UI started from Motif
  src/lib/                code shared by browser and server (schemas, models, stream parser)
  db/schema.ts            Drizzle schema: chat, message, attachment
  db/migrations/          generated by `pnpm db:generate`, applied by `void deploy`
  void.config.ts          Worker settings, AI Gateway, observability
  vite.config.ts          voidPlugin() before tanstackStart()
```

- **Server functions** (`createServerFn`) serve the app's own pages. The chat page loads its turns through one (`src/server/chat.functions.ts`).
- **`/api/*` server routes** serve anything that isn't a page RPC: multipart uploads, file downloads and answer streams. Their errors follow [api.md](api.md).
- **`*.server.ts`** modules never reach the browser bundle. TanStack Start's import protection fails the build if a client-reachable file imports one outside a server function handler.

## Request path

```text
browser ─▶ Worker (Void + TanStack Start)
             ├─ /c/:id page and its loader   ─▶ D1 (void/db)
             ├─ /api/chats/:id/messages      ─▶ R2 (void/storage), D1, then
             │                                  AI Gateway ─▶ Workers AI (void/ai)
             ├─ /api/chats/:id/answer        ─▶ AI Gateway ─▶ Workers AI
             └─ /api/chats/:id/files/:file   ─▶ R2
```

## Decisions

Each decision names the alternative it beat, so a later change can tell whether the reason still holds.

- **Void in framework mode, with TanStack Start.** Void infers bindings from imports (`void/db` means D1, `void/storage` means R2, `void/ai` means Workers AI), provisions them on deploy and applies migrations. TanStack Start brings routing, SSR, server functions and typed loaders. Void's own pages router was the alternative. TanStack Start was preferred for its ecosystem and for route types shared by loaders and links. The cost: `void/auth` doesn't run in framework mode, so auth would be wired by hand (Better Auth on D1 works, with its Drizzle adapter at `transaction: false`).
- **One Worker, no separate API server.** Pages, server functions and `/api/*` share one deploy, one origin and one session cookie. A separate API server would add CORS, a second deploy and a second set of secrets for no gain at this size.
- **D1 is the only database.** It's serverless SQLite on the same network as the Worker, and Void provisions it with zero config. D1 has no interactive transactions. Add Hyperdrive and Postgres only when the data needs it.
- **No accounts.** A random visitor id in an HttpOnly cookie owns each chat, which keeps the starter at zero config while chats stay private to one browser. The cost: clearing cookies loses the chats, the same person on two browsers is two visitors, and anyone with the URL can spend the account's AI allowance. Add auth and per-user limits before real use.
- **Free Workers AI models, through AI Gateway.** `@cf/*` models need no provider key and run on the account's daily free allowance. Every call names the gateway, so logs, cost and caching show in one place.
- **Motif for the chat UI.** The chat block from Motif (thread, composer, model picker, thinking block, scroll rail) was copied into `src/components` and adapted from Radix to Base UI (`render` instead of `asChild`). It is local code now: knip and lint cover it, and changes are not sent back to Motif. Being where the chat UI's appearance is defined, `components/{agents,scroll-rail,ui}` is exempt from the `shadcn/no-inline-styles`, `no-arbitrary-values` and `no-raw-colors` rules (motion values, brand marks, container-query sizes); `no-restyle` still applies.
- **Base UI under shadcn/ui.** The components were regenerated on the `base-nova` preset. Base UI has no `Form` registry item; forms use shadcn's `Field` with react-hook-form's `Controller`.
- **Retry is the design language.** [DESIGN.md](../DESIGN.md) is the spec and `packages/ui/src/styles/retry.css` holds its tokens. Both are this repo's own files; change them like any other design decision. Retry's component deltas (`DESIGN.md` › Components) are baked into `packages/ui/src/components`.
- **Vite+ for format, lint and test.** One toolchain (`vp fmt`, `vp lint`, `vp test`) replaces Biome, oxlint config files and a bare Vitest. `@shadcn/lint` rules run inside `vp lint`.
- **One flat error body for every `/api/*` error.** `{ code, message, issues?, traceId? }`, built by one helper and read by one client function. Clients branch on `code` and the status, and a `500`'s `traceId` is the `cf-ray` id, so a user's report finds the request in Workers Logs ([api.md](api.md)).

## Data and migrations

The schema lives in `apps/web/db/schema.ts`. Change it, then generate a migration:

```sh
pnpm db:generate
```

`pnpm dev` applies pending migrations to local D1 before it starts (`pnpm db:migrate` does it on demand). `pnpm run deploy` applies them to production. Never edit the database by hand.

## Extension points

These products aren't wired in. Void exports a module for each:

- KV: `void/kv`
- Queues: `void/queues`
- Email: `void/email`
- Durable Objects: `void/durable`
- Crons: one file per job in `crons/`

Each is one import away; Void provisions what the code imports.
